# Portfolio research and decision record

Research date: **2026-08-27**
Subject: **Akshit Ireddy — a design-led software engineer building AI characters, expressive desktop software, and practical tools**
Working identity thesis: **“I build software that feels alive.”**

This document records the evidence used to shape the four portfolio prototypes. It is a decision record, not a catalogue of trends to copy. The strongest recurring lesson is to create one authored interaction grammar that comes from the maker’s own work, while keeping project names, descriptions, links, and media in ordinary semantic HTML.

## What the evidence says for this portfolio

### Content hierarchy

The site should not be a reverse-chronological wall of repositories and should not lead with star totals. It should tell a present-tense story, then supply selective proof:

1. **Hero thesis — “I build software that feels alive.”** Use Akshit’s morphing GitHub-profile waveform as provenance for the visual language. Pair it with one plain sentence about expressive AI, desktop software, and tools.
2. **Right now.** Lead with **Alcove**, **Convai Desktop Pet**, and **Keyscape**. They are current, visually demonstrable, and jointly show warmth, characters, hardware, motion, and finish.
3. **Projects people found.** Give **Interactive LLM Powered NPCs**, **AI-Powered Video Tutorial Generator**, and **CupcakeAGI** a smaller, explicitly dated section. Stars are supporting context, not the headline. The framing should be “earlier experiments that travelled,” not “greatest hits.”
4. **Tools I wanted to exist.** Show **Transparency App**, **gifsmith**, **Email Briefing**, and **Compendium** as evidence of practical product instinct. One concise demo and one sentence per tool is enough.
5. **Archive / all repositories.** A terse link or compact index lets curious visitors continue without making old work define the landing page.

Use **“Selected work”** as the umbrella label. Do not claim every featured repository is open source without a per-repository license check: public source visibility is not the same as an OSI license, and some work has custom, absent, or third-party asset terms.

### Four prototype directions

1. **Signal Garden — strongest identity fit.** A calm, living signal derived from the existing profile waveform connects project “receivers.” The signature is movement that feels responsive rather than decorative. Keep all content as DOM; canvas/WebGL is a non-essential atmosphere layer with a quiet mode.
2. **Open-Source Cinema — strongest media fit.** One project occupies the stage while a reel/index changes the active work. It turns demos into authored scenes without creating an autoplay media wall. In production, call the page/collection “Selected work” even if the concept keeps its cinema nickname.
3. **Living Field Manual — strongest long-term editorial fit.** A designed working notebook of observations, diagrams, patches, and prototypes. It presents utilities and creative apps with equal dignity and can grow without an expensive 3D subsystem.
4. **Museum of Behaviors — boldest, highest-risk fit.** Projects are exhibits defined by behaviors—talks, walks, glows, teaches, organizes. Use an explorable entrance only; immediately offer a linear list and conventional case-study views. This direction has the largest accessibility, mobile, performance, and production-scope risk.

The prototypes are intentionally different interaction grammars, not four color skins. The first production recommendation is **Signal Garden**, with **Open-Source Cinema** as the strongest alternative if video demonstration becomes the primary job of the site.

### Media strategy

- Give the page **one active motion/video surface at a time**. Everything else begins as a lightweight still poster.
- Replace large animated GIFs with short, muted, looping **WebM/MP4** plus a **WebP/AVIF poster** where browser and source support allow. Keep GIF only when it is materially smaller or required by the destination.
- Cut project loops to roughly **8–15 seconds**, centered on one legible transformation. Link to a full demo, release, or repository for depth.
- The above-fold LCP should be real text or a small discoverable poster in initial HTML. Never lazy-load the LCP asset. Below-fold video should use `preload="none"`, explicit dimensions, a poster, and lazy/intent loading.
- Stop video and render loops when offscreen, when the tab is hidden, when another demo activates, and when quiet/reduced-motion mode is on. Reduced motion gets a deliberately composed still, not an empty canvas.
- Reserve intrinsic dimensions for every image/video to protect CLS. Keep project titles, descriptions, dates, and links in semantic HTML so the site remains understandable if media or WebGL fails.
- Treat **2 MB total first-view transfer** and **no offscreen demo download before intent** as project budgets to test—not universal web standards. Measure LCP, INP, and CLS on desktop and representative mobile hardware.
- Keep optimized short loops with the deploy only while the total remains modest. Put long/full-resolution demos on a dedicated CDN/object store and monitor transfer; do not grow the Git repository into a video archive.

### Vercel versus GitHub Pages

**Recommendation: use Vercel for prototype review and likely production, while keeping the build static and portable.** Unique preview URLs make four visual directions and later design rounds easy to compare. A custom domain, analytics, and a future contact/API room are available without redesigning the deployment workflow.

This recommendation has conditions:

- Keep the site as portable static output (for example, Vite or Astro-generated HTML/CSS/JS). It should remain deployable to GitHub Pages, Cloudflare Pages, or another static host without rewriting the visual layer.
- On Vercel Hobby, opt out of model training in Team/Project data preferences before connecting the repository. Recheck the terms at launch.
- If the site actively markets paid services or otherwise becomes commercial, use Vercel Pro or choose a host whose free tier permits that use.
- Do not assume Hobby Blob is a limitless video CDN: its current 1 GB storage / 10 GB transfer allowance is prototype-scale. Keep long demos on an appropriate external media service.

**Choose GitHub Pages instead** if the final site remains entirely static, the optimized media footprint is small, preview deployments are not important, and the tight GitHub-to-portfolio provenance is worth more than future server features. Its 1 GB published-site limit, soft 100 GB/month bandwidth limit, 100 MiB normal Git file ceiling, and lack of LFS support for Pages make media discipline mandatory.
